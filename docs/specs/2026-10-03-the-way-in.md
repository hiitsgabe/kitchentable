# The way in: the menu, and the first run

Built on [the benchmark](../benchmarks/2026-10-03-menus-and-first-run.md):
game menus, mobile onboarding, and what happens when a shared link lands on a
device that has never run the app.

## What it was

Five rows of the same size and weight. On a fresh install three of them were
greyed out saying "needs a source", and the one bright row was Sources,
labelled "start here". The whole first run was a wall with an instruction
written on it, and the brightest thing on the first screen was a data import.

## The menu

Four rows: **Play, Join, Decks, Settings**.

**Play is the way in, not the first of five.** It is drawn apart from the
list, larger, in the accent colour, and it holds the focus. Every menu in the
benchmark says the same thing: "the main call to action should be the most
dominant in your Main Menu UI", and hierarchy comes from "size, color
contrast, and placement". A list of five equal rows has no way in.

**Sources moved into Settings.** It is configuration, touched once, and by
the benchmark's rule about progressive disclosure, advanced settings belong
behind a menu rather than in front of the game. Settings' subtitle names
what is in it: your name, sources, network.

**Play and Join no longer shut themselves.** They were disabled without a
catalog, which is a wall with an explanation on it; the first run puts a
source in before the menu is ever reached, and somebody who skipped it can
still make a room and pick a deck inside it. Decks is the one row that
genuinely has nothing to show without cards, and it still says so.

## The first run

Three steps, each able to be skipped: **your name**, **where the cards come
from**, **a deck if you want one now**. Done is always available.

It follows the onboarding rules the benchmark sets out: get to the first real
outcome fast, cut what does not move toward it, let people skip, and ask at
the moment of intent. The name is asked for because it goes on a chair; the
source is asked for because the app ships with no cards; the deck is offered
and not required, because you can sit down at a table and pick one there.

## Arriving on a link, the first time

The room code is **parked before the wizard runs and replayed when it ends**.
This is the pattern the benchmark found in a real bug fix: "deep links
captured while signed out were sometimes discarded after onboarding; park the
pending navigation and let post-onboarding logic replay it". A link that
opens the menu is a link that did not work, and a link that opens the menu
after five minutes of setup is worse.

`Entry` holds the decision: a demo link, then the setup flag, then the room
code. While the flag is still being read off the disk it draws nothing rather
than the menu, because a flash of the menu in front of somebody who followed
an invitation is the same bug in miniature.

## Still open

Playing by yourself has no door. `PlayDecksScreen` is reachable only from a
room, so a solo table can only be had through "play all N hands here" inside
a room that contradicts it. Play means "make a table and invite people"; a
second way in that means "just deal me a table" is the missing one.
